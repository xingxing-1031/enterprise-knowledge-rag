# W6-2：真实运行适配器与服务组装

## 本阶段目标

把前面分别验证的 PostgreSQL、检索、工作流、模型生成和 FastAPI 组件组装成唯一可启动的真实服务，同时保留可替换、可测试的边界。

## 业务问题

只有协议和测试替身时，虽然每个算法单元可以测试，但网站仍不能访问真实知识库。直接把数据库、模型和会话逻辑写进接口又会造成强耦合，难以定位是数据、检索还是模型出错，也容易在测试启动时意外连接外部资源。

## 我的实现

`KnowledgeRepository` 同时实现增量写入、文档快照读取和授权 pgvector 查询，查询必须携带服务端决议后的文档版本集合。Embedding 和 Cross-Encoder 使用惰性加载的 sentence-transformers 适配器；回答生成使用 OpenAI 兼容结构化接口，可连接 Qwen 或 Ollama。`RuntimeChatService` 管理隔离会话、可见文档、管理员索引和评测报告，`bootstrap` 统一组装 LangGraph 与 FastAPI。

我还补齐了权限拒绝语义：受限制度只用服务端元数据判断相关性；普通用户无权时不会检索正文，也不会把标题或片段交给模型，工作流返回稳定的 `permission_denied`。

## 遇到的问题与取舍

本阶段数据库连接采用短连接工厂，方便先验证正确性；连接池放到 Docker 与交付阶段统一加入并做生命周期管理。sentence-transformers 只在第一次索引、查询或精排时加载，避免 API 导入就下载大模型，但首次真实请求会有冷启动成本。

当前查询改写使用确定性原问题透传，避免尚未评测的模型改写破坏时间、版本和权限含义。多轮指代消解会在 development 评测证明收益后再加入，不提前增加不可控变量。

## 我能口述的标准答案

我没有把真实依赖直接塞进 LangGraph 节点，而是让仓储、Embedding、Reranker 和结构化生成分别实现固定协议，再由 bootstrap 组装。这样单元测试可以用替身验证契约，生产入口又使用同一套工作流。权限过滤先于正文检索；即使最后答案没有引用受限文档，只要受限正文进入候选或模型上下文就已经算泄漏。
