# W5-1：LangGraph 企业 RAG 工作流

## 本阶段目标

把领域判断、受控改写、检索、证据、生成、引用校验和拒答接入可观察的状态流。

## 业务问题

端到端链路需要在越界、版本歧义、证据不足和引用失败时走不同分支。若所有逻辑都写在一个函数或 Agent Prompt 中，无法单独测试，也无法判断错误发生在哪个阶段。

## 我的实现

LangGraph 只保存共享状态和条件边。领域规则、检索和引用校验仍由独立服务实现。Trace 只记录节点、状态、耗时、候选数和证据数，不记录模型思维过程、Prompt 或受限正文。

## 验证结果

- LangGraph 分支与安全 Trace 专项测试：6 项通过。
- 全部 Python 回归：66 项通过，1 项 pgvector 环境测试明确跳过。
- 测试覆盖正常回答、越界拒绝、证据不足、版本歧义和连续引用失败后的降级路径。

## 遇到的问题与取舍

Trace 只记录可运维信息，不展示模型的隐藏思考过程。候选正文和 Prompt 也不进入普通 Trace，避免管理员调试能力反过来形成新的敏感信息泄漏面。

## 我能口述的标准答案

我使用 LangGraph 不是为了把普通函数都叫 Agent，而是因为链路存在明确状态和条件分支：越界问题直接拒绝，版本歧义不生成答案，证据不足不调用模型，引用失败有限重试后降级。每个确定性规则仍是独立服务，所以可以脱离大模型测试。

## 面试追问

- 为什么不用一个 Prompt 完成领域判断、检索和回答？
- Trace 为什么不展示模型完整思考过程？
- 哪些错误可以重试，哪些错误必须立即拒绝？
