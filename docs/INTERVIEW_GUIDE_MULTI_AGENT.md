# 多 Agent 面试讲解与追问

## 一分钟项目介绍

我把原来的企业知识库 RAG 升级成了一个按需多 Agent 企业运营助手。它不是所有问题都启动多个 Agent，而是由 Supervisor 先做结构化路由：普通问题走通用对话，制度问题走知识 Agent，经营指标问题走数据 Agent，只有跨制度和数据的复盘任务才启动协作。知识 Agent 保留权限、版本、混合检索、Reranker、引用和拒答；数据 Agent 通过内部接口调用另一个项目里的 Text-to-SQL、SQL 安全、业务一致性、审批和 MCP 报告能力。最后综合 Agent 只根据两类已验证结果生成答案，审核 Agent 再检查引用和数据证据是否齐全。

## 为什么需要多 Agent

不是因为多个 Prompt 看起来更高级，而是企业知识与经营数据拥有不同的数据源、安全边界和失败语义。知识 Agent 的成功条件是授权、有效且能支持结论的引用；数据 Agent 的成功条件是受治理查询成功并返回数据 evidence ID。把它们拆开后可以独立超时、降级、评测和审计，复杂任务再由 Supervisor 组合。

## 为什么不让所有问题都走多 Agent

多 Agent 会增加模型调用、网络开销和失败点。像“报销期限”只需要知识 Agent，“昨天订单数”只需要数据 Agent，“你好”只需要通用对话。只有“分析退款率变化，并判断是否触发售后制度”同时需要两类受治理证据，协作才带来真实收益。

## Supervisor 如何工作

Supervisor 输出严格的 `AgentPlan`，包含模式和任务步骤。明显的制度、数据和协作信号由确定性规则先保护，避免模型不可用时完全失去路由；真正模糊的通用请求可以由结构化模型规划。模型不可用或输出不合法时回退到保守规则，企业事实不会降级成自由聊天回答。

## Agent 是否真的独立

独立指职责、上下文、工具权限、输入输出契约和成功条件独立，不要求每个角色使用不同大模型。知识 Agent 只能访问授权知识；数据 Agent 只能通过内部接口使用受治理查询；综合 Agent 看不到数据库凭据；审核 Agent 使用结构化 evidence ID 和引用做确定性检查。

## 如何避免两个项目循环调用

项目一原本会调用项目二补充制度证据。如果项目二调用项目一时仍开启这个能力，就会出现循环。内部 `/internal/agent` 请求明确设置 `include_knowledge=false`，项目一只执行数据能力；同时项目二 `/internal/evidence` 强制绕过 Supervisor，直接走纯知识链路。

## Reviewer 检查什么

- 知识结论是否存在真实 Citation。
- 数据结论是否存在查询或指标 evidence ID。
- 协作模式要求的知识与数据子任务是否都完成。
- 缺少任一核心证据时返回 degraded 或 refused，不伪装成完整成功。

## 当前评测怎么讲

我建立了 26 条合成 development 路由样本，覆盖通用、知识、数据、协作以及容易误判的反例，当前路由和角色选择都是 26/26。它只是路由契约评测，不是通用 Agent 准确率。端到端任务还需要分别报告知识引用、数据证据、工具成功率、延迟和协作完成率。

## 已知限制

- 当前 Supervisor 的安全回退以规则为主，复杂模糊意图仍依赖结构化模型。
- 数据 Agent 调用项目一是同步 HTTP，已设置超时和可信降级，但还没有分布式任务队列。
- 综合 Agent 输出经过证据存在性审核，但更细粒度的“每句话对应证据”仍主要由知识引用校验承担。
- 当前为个人合成数据演示，不等同于真实企业多租户上线。
