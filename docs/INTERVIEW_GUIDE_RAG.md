# 企业知识库 RAG 面试讲解

## 一句话介绍

我独立实现了一个可审计的企业知识库 RAG 服务，重点解决“企业制度不能靠模型常识猜”的问题：文档先经过解析、清洗、切分和权限治理，再通过 BM25、向量、RRF 和 Reranker 召回证据，最后只基于满足覆盖要求的证据生成回答，并返回引用；证据不足时拒答。

## 检索链路

1. 根据用户身份过滤部门、角色、版本和生效时间。
2. 关键词检索补足精确术语，向量检索补足语义表达。
3. 用 RRF 融合不同召回结果，再用 Reranker 对候选重排。
4. 生成结构化证据需求，检查每个需求是否被授权片段覆盖。
5. 覆盖不足时只在已路由文档范围内进行有限补充检索，仍不足则拒答。
6. 输出答案、引用、版本和局限，供项目一展示或审计。

## 管理控制面

网页登录只保留 `knowledge-admin-demo` 一个管理员身份。普通用户不能通过本项目登录、查看文档或直接问答，项目一通过 `X-Internal-Token` 调用 `/internal/evidence`。管理员控制台把导入审核、生命周期、检索诊断和评测分开，避免把内部调试接口误当成员工聊天接口。

检索实验室只展示每阶段候选数量、授权排除数量、文档元数据、通道排名和分数，切片正文不进入调试响应。永久删除会在数据库事务中级联清理切片和向量，源文件删除前校验绝对路径必须位于知识目录或上传目录，审计记录只保存 HMAC 文档引用。

## 高频追问

**为什么不只用向量检索？** 企业制度中“报销”“发票”“生效日期”等词非常关键，BM25 对精确词更稳；向量检索负责同义改写，RRF 让两类信号互补。

**Reranker 放在哪里？** 先扩大候选集，再对候选进行交叉编码或远程重排。它不是召回器，不能弥补候选集完全没有目标文档的问题，所以需要单独评测 Recall 和引用准确率。

**如何防止越权？** 权限过滤发生在候选生成前，并且二跳检索只能访问首跳已授权且已路由的文档集合。回答层再次校验引用属于本次检索结果。

**什么时候拒答？** 证据需求无法被当前生效版本和用户权限覆盖时拒答，不让模型用常识补写制度条款。

**项目一如何调用？** 项目一只调用 `/internal/evidence`，通过 `X-Internal-Token` 认证；本项目不调用项目一，职责和依赖方向保持单向。
