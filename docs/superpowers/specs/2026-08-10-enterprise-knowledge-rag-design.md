## 1. 项目目标

构建一个面向企业员工的制度与流程知识库助手。系统接收自然语言问题，从企业制度、办事流程和操作规范中检索最小充分证据，返回带文档、章节、版本和生效日期引用的中文答案；证据不足、文档过期或用户无权访问时拒绝回答。

项目用于秋招和实习投递，重点证明非结构化企业知识场景下的 RAG 工程能力，而不是伪装成真实企业实习或正式生产系统。

### 1.1 目标用户

- 普通员工：查询请假、报销、采购、入职、信息安全等制度和办理流程。
- 部门员工：查询仅本部门可见的补充规定。
- 知识库管理员：查看文档状态、版本、索引结果和评测报告。
- 面试官或演示访客：无需了解项目内部结构即可体验成功回答、版本冲突、权限拒绝和证据不足四类场景。

### 1.2 核心价值

- 缩短员工在多份制度和流程文档中查找答案的时间。
- 避免旧版本制度覆盖当前生效规则。
- 防止模型引用用户无权访问的内部文档。
- 让每个结论都能回到实际文档章节核验。
- 当证据不足时拒答，不用模型常识补齐企业规则。

## 4. 业务语料设计

项目使用明确标注为“为项目评测构造”的脱敏企业制度语料，不冒充真实公司内部文件。最终规模以实际生成和验收结果为准，README 只记录可复现的真实数量。

首批覆盖以下主题：

- 人力资源：请假、加班、入职、转正、离职和远程办公。
- 财务：差旅、费用报销、借款、发票和付款审批。
- 采购：采购申请、供应商准入、合同和验收。
- 信息安全：账号权限、数据分级、设备使用和安全事件上报。
- 行政：印章、会议室、固定资产和访客管理。

语料必须主动包含可测难点：

- 同一制度的旧版、现行版和未来待生效版。
- 总部制度和部门补充规定。
- 标题相似但适用对象不同的流程。
- 包含表格、列表、例外条款和交叉引用的章节。
- 已废止文档和重复上传文档。
- 权限受限文档。
- 知识库没有答案的问题。

## 5. 数据模型

### 5.1 DocumentRecord

```text
document_id        稳定文档标识
title              文档标题
document_type      policy / process / handbook / faq
department         发布部门
visibility         public / department / restricted
allowed_roles      可访问角色集合
version            语义版本，如 2.1
status             draft / active / expired / revoked
effective_from     生效时间
effective_to       失效时间，可为空
supersedes_id      被替代的旧文档标识，可为空
content_hash       去重与增量索引依据
source_path        原始文件相对路径
indexed_at         索引时间
```

### 5.2 ChunkRecord

```text
chunk_id           稳定片段标识
document_id        所属文档
section_path       标题层级路径
chunk_index        文档内顺序
content            清洗后的正文
token_count        估算 token 数
content_hash       片段哈希
embedding_model    向量模型版本
```

### 5.3 RetrievalEvidence

```text
evidence_id        单次证据标识
chunk_id           引用片段
document_id        引用文档
title              文档标题
section_path       章节路径
version            文档版本
effective_from     生效日期
retrieval_channels 命中的召回通道
retrieval_rank     融合后排名
reranker_score     精排分数
quote              用于回答的最小引用内容
```

前端和模型只能使用权限过滤、版本决议完成后的 `RetrievalEvidence`，不能接触被过滤的候选片段。

## 6. 系统架构

```text
文档导入
-> 解析与标准化
-> 标题感知切分
-> 元数据校验
-> 去重与版本登记
-> 增量生成 Embedding
-> PostgreSQL/pgvector 持久化

用户问题
-> 请求与身份校验
-> 领域判断
-> 受控查询改写
-> 权限/状态/生效时间预过滤
-> BM25 召回 + 向量召回
-> RRF 融合
-> Reranker 精排
-> 版本冲突决议
-> 最小充分证据构建
-> 基于证据生成答案
-> 引用一致性校验
-> 返回答案、引用、状态和检索轨迹
```

LangGraph 只负责有状态编排、分支和有限重试。文档解析、检索、权限、版本和引用校验保持为独立可测试服务，不把所有逻辑塞进图节点。

## 7. 检索设计

### 7.1 查询处理

- 领域判断只区分企业知识问题、闲聊和越界问题。
- 查询改写必须保留原问题，并记录改写结果。
- 多轮指代消解只补全已在历史中明确出现的制度、部门或流程。
- 时间、版本和权限条件由结构化规则处理，不交给模型自由决定。

### 7.2 候选召回

- BM25 负责制度名称、编号、部门和专有术语精确命中。
- bge-m3 向量检索负责同义表达和语义相近问题。
- 每路返回独立排名，不能直接比较原始分数。
- 使用 RRF 按排名融合，并保留每个候选的通道和原始排名。
- Reranker 只重排已召回候选，不能弥补召回缺失。

### 7.3 元数据和版本约束

- 召回前过滤用户无权访问的文档。
- 默认仅使用查询时间点已生效且未失效的文档。
- 用户明确询问历史规则时允许指定历史时间。
- 同一制度存在多个符合版本时，使用版本关系和生效时间确定唯一有效版本。
- 版本冲突无法确定时拒答，并提示用户补充时间或联系管理员。

### 7.4 最小充分证据

- 回答前从精排结果中选择覆盖问题所需事实的最少片段。
- 同一章节重复片段去重。
- 互相冲突的片段不能同时直接交给生成模型。
- 证据必须包含稳定文档、章节和版本标识。

## 8. 回答、引用与拒答

### 8.1 回答原则

- 只根据 `RetrievalEvidence` 回答。
- 企业规则、金额、时间和审批层级必须能在引用中找到。
- 答案使用中文，文档编号、版本和技术标识按原文保留。
- 不把模型常识写成企业制度。

### 8.2 引用校验

- 每条引用必须对应本次证据中的实际 `chunk_id`。
- 引用的文档版本必须与证据一致。
- 答案中的关键数字、日期和审批层级必须能在引用文本中匹配。
- 引用校验失败时允许有限重生成；再次失败则返回证据摘要和降级说明。

### 8.3 拒答类型

- `out_of_scope`：不是企业制度或流程问题。
- `insufficient_evidence`：知识库没有充分依据。
- `permission_denied`：存在相关内容但当前用户无权访问，不泄露标题和片段。
- `version_ambiguous`：无法确定用户询问的制度版本或时间。
- `service_failed`：模型、索引或数据库发生技术故障。

普通用户看到稳定中文提示；管理员调试接口才能查看英文错误类型和检索轨迹。

## 10. 评测设计

### 10.1 数据隔离

- development 用于定位问题和优化。
- frozen holdout 在系统定版后只运行一次。
- 运行过并据此调参的 frozen 集自动降级为 development，不能继续宣称未见测试。
- 固定语料快照、索引版本、Embedding、Reranker、LLM、提示词和随机参数。

### 10.2 分阶段指标

- 领域判断准确率。
- Recall@K：正确证据是否被召回。
- MRR 和 nDCG：正确证据排名质量。
- 权限泄漏率：必须为 0。
- 版本选择准确率。
- 引用命中率与引用一致性。
- 正确拒答率和错误拒答率。
- 最终答案正确率，由规则检查和人工盲审共同完成。
- P50/P95 延迟和模型调用次数。

### 10.3 对比实验

固定其他变量，只比较：

1. 向量检索 baseline。
2. BM25 + 向量 + RRF。
3. BM25 + 向量 + RRF + Reranker。

不能只报告最好一次；需要多次运行并报告平均值、波动、延迟和资源成本。只有实际运行结果可以进入 README 和简历。

## 11. 技术栈与工程边界

- Python 3.11/3.12。
- FastAPI、Pydantic v2、LangGraph。
- PostgreSQL 16 + pgvector 作为文档元数据、片段和向量的单一持久化来源。
- jieba + rank-bm25 构建受版本控制的词法索引缓存。
- bge-m3 Embedding，bge-reranker-v2-m3 精排；配置允许替换模型。
- OpenAI 兼容 LLM 适配器，同时支持远程 Qwen 和本地 Ollama。
- React 18 + TypeScript + Vite 作为 Web 演示端，避免继续扩展旧 UniApp 页面。
- pytest、Ruff、TypeScript 检查和前端构建进入 CI。
- Docker Compose 编排 PostgreSQL、API 和前端发布产物。

采用 React 是为了复用项目一已经掌握的部署和交互经验，同时让企业文档引用、版本和检索过程更适合桌面演示。项目二的竞争力来自 RAG 深度，不以多一种前端框架为卖点。

## 12. 错误处理与可观测性

- 文档解析失败按文件记录，不允许静默跳过。
- Embedding、Reranker 和 LLM 调用使用有限重试和明确超时。
- 权限拒绝、证据不足和技术失败使用不同状态。
- Trace 记录每阶段耗时、候选数、过滤数和失败原因，但不记录密钥和受限正文。
- 回答生成失败且证据可信时，可降级返回证据摘要；检索或权限边界失败时不能降级成自由回答。

## 13. 测试策略

- 单元测试：元数据模型、版本决议、权限过滤、RRF、引用校验和拒答策略。
- 集成测试：文档导入到检索证据、问答到引用返回、权限不可泄漏。
- 数据库测试：空库迁移、种子导入、增量更新、重复文档和版本替换。
- API 测试：中文错误、SSE 事件顺序、会话隔离和管理员边界。
- 前端测试：关键状态渲染和移动端无横向溢出。
- 端到端演示：成功回答、历史版本、权限拒绝、证据不足各至少一个固定场景。

## 16. 完成标准

- 新项目不依赖旧项目绝对路径即可在干净环境运行。
- 原重庆文旅仓库保持不变。
- 至少完成四类固定演示：正常回答、历史版本、权限拒绝和证据不足。
- 每个答案引用真实存在的文档、章节、版本和生效日期。
- 权限泄漏自动化测试为 0。
- 三种检索方案在同一语料快照上完成受控对比。
- frozen holdout 在定版后只运行一次，并保留原始报告。
- README、学习日志、演示页面和简历数字互相一致。
- 用户能够讲清 RRF、Reranker、元数据过滤、版本决议、引用校验和拒答边界。
