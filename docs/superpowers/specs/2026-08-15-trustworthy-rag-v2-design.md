# 可信 Agentic RAG v2 设计

## 1. 背景与目标

项目二作为知枢 Nexus 的可信证据后端，现有链路已经具备文档解析、版本治理、权限过滤、混合检索、Reranker、引用校验和拒答能力，但真实 development 报告暴露出以下问题：

- 证据覆盖判定会把一个高相关候选错误地视为支持多个证据需求，导致迭代检索没有触发。
- 英文问题检索中文制度时，父文档路由可以成功，但基于 token 重叠的覆盖判定可能错误拒绝证据。
- 分层检索在路由前移除了受限文档，无法稳定区分权限不足和证据不足。
- 父文档路由文本只包含标题、类型、部门和一级标题，细粒度业务问法容易路由失败。
- 新增零售制度未进入旧评测快照，部分零售问法还会被领域判断提前拒绝。
- 评测异常只记录宽泛的 `ModelProviderError`，缺少阶段级定位和延迟信息。

本次升级目标是形成一套可解释、可审计、可受控评测的 Agentic RAG 链路。系统应根据查询生成结构化证据需求，在证据不完整时进行有界的迭代补充检索，并在权限、版本或证据不足时给出正确且不泄漏信息的拒答。

## 2. 术语与简历表达

项目内部保留 `hop_count` 和最多两跳的执行约束，用于限制延迟、模型调用和检索范围。对外文档与简历不把“二跳”作为孤立卖点，而使用以下行业通用表达：

- Agentic RAG：由规划器决定需要哪些证据以及是否继续检索。
- Query Decomposition：把复合问题拆成独立、可验证的 evidence needs。
- Iterative Retrieval：根据未覆盖的证据需求触发补充检索。
- Multi-hop Retrieval：需要跨章节或跨文档组合证据时执行多阶段检索。

简历推荐描述为：“基于 Query Decomposition 将复合问题拆分为结构化证据需求，并按证据缺口触发有界 Iterative Retrieval，在权限与证据预算约束下完成跨文档证据聚合。”

## 3. 范围

### 3.1 本次实现

- 修复多需求证据覆盖假阳性。
- 支持中英文跨语言的语义证据覆盖。
- 允许补充检索根据缺失需求重新扩展授权范围内的父文档。
- 正确区分 `permission_denied`、`insufficient_evidence` 和 `version_ambiguous`。
- 丰富父文档路由表示，覆盖二级章节和有限正文摘要。
- 扩展企业领域判断至零售退款、运营复盘等现有语料主题。
- 增加语料快照与评测报告新鲜度检查。
- 增加阶段级异常、延迟与生成质量指标。
- 建立 development-v2 和新的 frozen-holdout-v2。

### 3.2 不在本次范围

- 分布式任务队列和独立向量数据库集群。
- 面向真实客户的多租户计费、SLA 或容量承诺。
- 为制造评测数字而批量复制相似知识文档。
- 将旧 frozen holdout 重新包装为未见集。

## 4. 总体架构

请求继续沿用现有 LangGraph 工作流：

1. 查询改写器结合最近对话，将省略主语的追问改写为独立可检索问题。
2. 领域判断确认改写后的请求属于企业知识范围。
3. 查询规划器将问题拆成最多四个结构化 evidence needs。
4. 权限与版本服务生成当前用户可访问的文档版本集合，同时保留不泄漏正文的受限元数据匹配能力。
5. 父文档路由在授权集合内执行 BM25 与向量 RRF。
6. 章节检索执行 Vector、Hybrid RRF 或 Hybrid RRF + Reranker。
7. 证据覆盖服务逐个 need 判断候选支持关系。
8. 如果存在未覆盖的必需 need 且预算允许，使用该 need 的查询重新路由并执行一次补充检索。
9. 引用生成器仅使用最终已验证证据回答；权限、版本或证据不满足时进入对应拒答分支。

最多两跳是运行预算，不是算法名称。第一阶段解决主要证据，第二阶段仅针对缺失需求补证，禁止无界循环。

## 5. 组件设计

### 5.1 EvidenceCoverageService

覆盖判定以 need 为单位，而不是以整句问题为单位：

- 词法重叠达到阈值时，可以直接建立候选到 need 的支持关系。
- 当词法重叠不足时，使用注入的语义 scorer 对 `need.query` 与候选段落单独评分。
- 整句主查询的高相关分数只能辅助单 need 计划，不能让一个候选自动覆盖多 need 计划中的所有需求。
- 每个候选输出明确的 `supports_need_ids`，最终覆盖率只由这些关系计算。
- scorer 不可用时退化为词法判定，并留下可观察的 degraded 状态，不伪造语义覆盖。

### 5.2 Iterative Hierarchical Retrieval

第一次父文档路由使用 `plan.primary_query`。若必需 need 未覆盖，补充阶段使用 `topic + need.kind + need.query` 重新在授权文档集合中路由，合并新的父文档范围后检索章节。

补充阶段遵守以下边界：

- 最多执行一次补充阶段。
- 每个缺失 need 最多发起一次检索。
- 新路由仍只能看到服务器计算出的授权版本集合。
- 合并候选时按 chunk ID、内容哈希和文档版本去重。
- 最终证据仍受条数和 token 预算限制。

### 5.3 权限拒答

权限判定分为元数据匹配和正文访问两个层次：

- 受限文档正文和 chunk 永远不进入未授权用户候选集。
- 系统可以使用经过清洗的标题、部门、文档类型和主题标签判断问题是否明确指向受限制度。
- 如果最终没有可回答的授权证据，但存在查询相关的受限元数据命中，返回 `permission_denied`。
- 如果最终没有可回答的授权证据，且没有相关受限命中，返回 `insufficient_evidence`。
- 对外拒答不包含受限文档标题、ID、正文或审批数值。

### 5.4 父文档路由表示

`document_search_text` 包含：

- 文档标题、类型、部门和 topic tags。
- 一级与二级章节标题。
- 每个二级章节的首个受控摘要句，设置总字符上限，避免把整个文档复制到父级索引。

文档更新后重新生成父级表示和 embedding；索引新鲜度检查比较磁盘语料快照、数据库内容哈希与最新评测快照。

### 5.5 领域判断

保留确定性快速判断，但词表必须覆盖仓库当前主题，包括退款、退货、售后、运营复盘、销售、门店、指标和经营分析。契约测试从 development-v2 读取所有 `expected_in_scope=true` 的题目，确保新增语料对应问法不会在检索前被拒绝。

多轮追问不由词表单独决定：后续会话若包含省略主语，应结合最近一轮企业知识上下文完成查询改写，再对改写结果执行领域判断。

## 6. 数据与评测设计

### 6.1 Development v2

目标规模为 60 至 80 条，所有答案和 gold evidence 由语料人工标注，不由待测模型生成。覆盖要求：

- 24 个逻辑文档每个至少两个正向问法，历史版本按逻辑文档单独标注。
- 至少 12 条跨章节或跨文档组合题。
- 至少 12 条权限题，覆盖 employee、department_admin、knowledge_admin 和跨部门身份。
- 至少 8 条版本题，覆盖历史、当前、未来草稿和歧义。
- 至少 12 条鲁棒性题，覆盖口语、错别字、简称、多轮追问和中英跨语言。
- 至少 8 条拒答题，覆盖超范围、缺少证据、权限不足和提示注入。
- 新增零售退款与运营复盘制度的正向、拒答和组合问题。

相似条款干扰数据单独标记为 synthetic distractor，只用于测量检索退化，不冒充真实企业数据。

### 6.2 Frozen Holdout v2

在代码、Prompt、阈值和 development-v2 结论固定后创建 20 至 30 条新题。运行器继续执行一次性消费锁定。旧 holdout 和报告作为历史审计记录保留，不覆盖、不删除、不重新称为未见集。

### 6.3 指标

保留现有 Recall@K、MRR、NDCG、版本准确率、权限泄漏率和延迟指标，并新增：

- Citation Recall 与 Citation Precision。
- 必需事实完整率和无依据事实率。
- 拒答 Precision、Recall、F1 及原因混淆矩阵。
- need-level coverage precision，防止假覆盖。
- 多跳触发准确率与迭代检索完成率。
- 跨语言成功率、改写一致率和多轮追问成功率。
- planner、routing、embedding、retrieval、reranker、generation 各阶段 P50、P95、P99。
- 超时率、模型异常率、重试次数、模型调用数和可获得时的 token 成本。
- 评测报告相对当前语料的 snapshot freshness。

所有简历数字必须来自提交到 `evaluation/reports/` 的报告，注明合成语料、用例数、语料快照、模型和重复次数。

## 7. 错误处理与可观察性

- 模型边界继续隐藏供应商原始响应和密钥，但异常必须带安全的阶段代码，如 `planner_provider_error`、`embedding_provider_error`、`reranker_provider_error`、`generation_provider_error`。
- 单题异常保留在评测分母中。
- 工作流 trace 记录每个阶段的耗时、候选数、覆盖 need 数和 hop 数。
- 远程模型失败采用有限重试和退避；不可重试的结构校验错误直接失败。
- 达到时间预算后返回稳定降级或拒答，不无限等待。

## 8. 测试边界

测试围绕以下公开接口编写，执行逐条 red-green 循环：

1. `EvidenceCoverageService.cover`：验证单 need 语义桥接、多 need 独立覆盖和跨语言覆盖。
2. `HierarchicalRetrievalService.retrieve`：验证缺失 need 重新路由、授权边界和拒答原因。
3. `RuntimeChatService.run_knowledge`：验证领域判断、多轮上下文和完整工作流结果。
4. `POST /internal/evidence`：验证项目一调用时的身份映射、证据字段、拒答和不泄漏行为。
5. `EvaluationRunner.run`：验证新增指标、阶段错误、异常入分母和快照新鲜度。

单元测试使用确定性 scorer 和仓库替身；关键链路增加 PostgreSQL/pgvector 集成测试；真实 API 只用于 development 实验，不作为日常测试前提。

## 9. 验收标准

- 已知两道多需求问题不会再由单个不完整候选假覆盖全部 need。
- 英文询问中文制度时，正确证据可以通过语义覆盖判定。
- 普通员工明确查询受限付款制度时返回权限拒答且无正文泄漏。
- 资产遗失、零售退款和运营复盘问法能够进入正确领域与父文档。
- development-v2 覆盖所有逻辑文档和规定的角色、版本、多跳、鲁棒性场景。
- 新报告的语料快照与当前语料一致，三种策略使用相同变量各重复三次。
- frozen-holdout-v2 只在最终条件固定后消费一次。
- 全量自动化测试、前端构建和必要的数据库集成测试通过。
